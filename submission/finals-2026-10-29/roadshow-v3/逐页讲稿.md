## 第1页 · CJ-DocGuard

各位评委好，我的作品是 CJ-DocGuard，面向仓颉项目级 API 文档生成及测试。它把接口说明、登记示例、开发工具包版本和检查结果放到同一个本地工作台中，供库维护者查询、测试和导出。

现场动作：停留封面，介绍作品目标。

## 第2页 · 三项交付对应一套工作流程

作品对应赛题的三项交付。第一，提取公共声明，生成包含参数、返回类型和关联示例的结构化文档。第二，使用真实仓颉工具链编译和运行登记示例，再检查输出。第三，分别记录不同开发工具包和平台的结果，同时检查文档中的目标文件与锚点。三项能力都能从网页进入。

现场动作：按表格从需求指向入口及产物。

## 第3页 · 接口说明与示例可以一起检索

这里是最新版的实际页面。搜索 add 后，页面显示函数声明、两个整数参数、返回类型和关联示例，并能打开当前源码。当前工作区提取了四十七个公共接口，登记十四个示例。接口数量描述提取结果；一个接口出现在文档中，并不代表它的所有行为都已验证。

现场动作：指向 add 声明、参数、返回类型与关联示例；不逐个念导航。

## 第4页 · 网页可完成查询与示例包导出

现在切到网页。先检索接口，再查看对应的测试矩阵。接着选择有效示例查询，指定 SDK 一点二点零和当前平台，查询 arithmetic。完成后导出同一示例的 ZIP 包。查询和导出都会检查当前输入；这里调用的是本地仓颉服务。全量矩阵已在准备阶段运行，现场不把已有记录说成刚刚重新编译的结果。

现场动作：0–15秒检索add；15–30秒查看矩阵并区分仅编译；30–55秒查询SDK1.2.0/arithmetic；55–75秒导出同一示例；75–80秒返回PPT。等待超过8秒切到本页截图。

## 第5页 · 仓颉承担本地服务与核心处理

实现上，浏览器使用 HTML、CSS 和 JavaScript。本地 HTTP 服务、声明提取、配置处理、测试编排和当前结果判断使用仓颉。两版 SDK 调用的都是真实编译器和运行库。C 负责子进程监督，Bash 负责构建启动；Python 用于测试和辅助工具，不承担正式网页服务。

现场动作：沿架构图从浏览器讲到仓颉服务、核心及SDK；明确语言分工。

## 第6页 · 当前矩阵保留运行与仅编译的区别

本版当前矩阵有二十八条独立记录。SDK 一点一点三和一点二点零，各有十三条运行通过、一条仅编译，合计二十六条运行通过、两条仅编译。运行通过要求程序成功执行且登记输出检查通过。仅编译没有验证运行行为，因此单独展示。这组数字描述当前样例，不作为全部仓颉项目的准确率。

现场动作：指向两版SDK柱形图，再核对表格中13+1=14。

## 第7页 · 输入变化后，旧结果需要重新测试

结果不仅关联示例名称，还关联源码、配置、工具链和平台。输入变化后，旧记录需要重新测试。最新一次检查失败时，也不能退回较早的成功记录。查询与导出使用相同规则，历史记录继续保存，供追溯查看。这样可以避免把过去的成功直接当作当前可用。

现场动作：说明输入匹配、真实执行和输出检查；用源码变化与最新失败两个分支解释。

## 第8页 · 链接问题可以定位到来源与原因

链接检查不仅统计数量，还给出来源、行号、原始目标和原因。本轮重新检查的专项样例中，预置的缺失文件和不存在锚点都被定位到 README 的对应行。严格检查返回一，表示它确实发现了这些问题。离线未检查的外部链接保持未确认，不显示为通过。

现场动作：指向README第13、14行，区分预置问题被检测和工具自身失败。

## 第9页 · 决赛最新版完善了操作与任务反馈

最新版进一步补齐了工作台操作。下拉选项对应实际配置和记录，查询条件随工具切换；任务状态区分排队、运行和结束，未提供数量时不编造进度百分比。大量历史记录触发的任务内存问题也已处理。最新二十三项原生服务回归通过，三档尺寸共三十次页面检查通过，七百三十九条历史记录继续保留。

现场动作：按操作、状态、历史三组讲当前实现；不作阶段数据对比。

## 第10页 · 源码与运行说明可供评委复查

评委可以从公开仓库获取固定版本，按指南配置两版仓颉工具包和兼容系统 SDK，再构建并启动工作台。当前完整实测环境是 macOS arm64。作品交付的是可操作、可重复检查的文档和测试流程。谢谢各位评委。

现场动作：展示源码068a22a和指南入口；结束主讲，按追问选择备查页。
