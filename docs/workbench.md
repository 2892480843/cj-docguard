# CJ-DocGuard 本地网页工作台

**当前正式本地服务已迁移为仓颉实现。** 构建、启动、源码编辑和中断恢复见 [原生工作台指南](native-workbench.md)。此前 Python 服务只保留为测试对照。

工作台把原生命令行的文档、验证、查询和导出能力接入本地浏览器。所有执行和证据准入仍由仓颉核心负责。页面、脚本和字体不依赖外部 CDN，无需 Node.js 或前端构建。

## 启动

需要 Python 3.11+、C 编译器，以及已登记的仓颉 SDK。SDK 安装和环境变量见根 README。

```bash
bash scripts/build_workbench.sh
bash scripts/workbench.sh --port 8765
```

在浏览器打开 `http://127.0.0.1:8765`。服务只绑定本机，关闭启动终端中的服务即可停止。不要将端口通过代理公开到网络。

macOS 新版 Xcode 的系统 SDK 可能无法被旧仓颉 SDK 附带的链接器读取。遇到 `unknown architecture arm64e.x1` 时，显式选择本机已有且兼容的系统 SDK；路径须按实际安装调整：

```bash
export CJ_DOCGUARD_SYSTEM_SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX15.4.sdk
bash scripts/build_workbench.sh
bash scripts/workbench.sh --system-sdk "$CJ_DOCGUARD_SYSTEM_SDKROOT" --port 8765
```

选择是显式的，不修改系统 Xcode 配置、不自动下载系统 SDK。原生验证环境记录规范化 SDKROOT 路径；仍不构成整个宿主操作系统的内容证明。

## 第一次使用

默认登记 `build/workbench/projects/demo` 下的自建健康样本副本。它与 `examples/healthy` 分开，默认不复制历史报告。首次进入没有报告是正常状态：先“诊断环境”，再“构建索引”，最后“运行验证”。默认样本登记 14 个示例，两个 SDK 共 28 格；其中 2 格只编译，不算行为运行验证。

在“项目与配置”中可以登记已有 `docguard.toml` 的绝对路径，或在不存在的绝对目录创建示范项目。新项目保持 `trusted=false` 和 `closed_inputs=false`，维护者审核源码、导入、外部输入和断言后，才编辑配置允许执行。网页不自动提升信任。

配置编辑器校验 TOML 语法并原子保存，完整业务字段、源码范围及执行约束仍由原生命令检查。配置保存不会自动执行示例。

## 页面与操作

| 页面 | 用途 |
|---|---|
| 项目概览 | 接口数、登记示例、报告状态、环境信息和演示引导 |
| 接口文档 | 搜索声明、按类型筛选、查看所属类型、注释、源码和关联示例 |
| 可执行示例 | 查阅配置中登记的程序、断言和各 SDK 记录 |
| SDK 验证矩阵 | 筛选示例与状态，打开单格完整证据 |
| 任务中心 | 环境诊断、构建、验证、严格检查，查看日志与退出码，取消任务 |
| 问题与诊断 | 编译、运行、断言、链接和提取诊断 |
| 历史与对比 | 冻结历史与两个报告快照的变化 |
| AI 证据查询 | 三种原生只读查询，显示实际请求和响应 |
| 项目与配置 | 登记项目、初始化和编辑配置 |

任务全局串行；运行时再次启动操作会被拒绝，避免与原生 writer.lock 冲突。任务日志有界并可轮询；原生编译器逐例日志会在证据目录保存，详情页可查看已有报告中的日志。取消操作发送中断信号并等待清理，超时才升级终止。工具不自动删除残留 writer.lock。

导出需选择明确的示例、SDK 与平台。核心重新检查当前输入和环境，只有符合准入条件的运行示例才会生成可下载 ZIP。解压后按 `build.sh` 使用对应真实 SDK 重建。

## 现场演示路径

1. 在默认隔离副本中构建并运行双 SDK 验证，查看矩阵和断言。
2. 查询 `get_verified_examples`，选择实际 SDK 和平台，确认返回当前有效记录。
3. 点击“注入故障”，只修改工作台拥有的算术示例副本。
4. 先执行检查或当前查询，观察旧证据被拒绝；再验证，查看实际值与预期值的差异。
5. 点击“恢复源码”，重新验证，再查询并导出有效示例。
6. 解压导出包，使用对应 SDK 执行 `build.sh`。

这是操作指引，不是预设的成功结果。SDK 缺失、编译失败、过期、取消和断言失败都会保留对应状态。

## 数据与边界

- 工作台状态默认位于 `build/workbench/`，可用 `--state-dir` 指定其他位置；项目登记持久化，任务列表属于当前服务会话。原生执行历史仍在各项目输出目录。
- 报告始终标记快照。`CURRENT` 只说明生成或查询时的输入匹配；任何后续修改都需要重新检查。
- 历史接口统一返回 `FROZEN`、`eligible=false`，不将归档结果变成当前证据。
- 本地服务只提供固定操作，没有任意 shell 命令接口。写请求要求同源和会话令牌，并检查 Host。
- 工作台不是安全沙箱，仍仅适用于维护者已审核的本地项目。Windows、多包构建、完整语义分析等支持边界沿用原生核心。
- AI 页面是原生工具查询界面；不自动连接模型，也不宣称已经在其他 AI 客户端完成接入。

实测结果与初赛差异见 [2026-10-29 验收记录](workbench-verification-2026-10-29.md)。

## 验证入口

```bash
python3 -m unittest discover -s tests -p 'test_workbench*.py' -v
python3 -m unittest discover -s tests -p 'test_system_sdk.py' -v
python3 scripts/validate_workbench.py --url http://127.0.0.1:8765
```

最后一个入口通过真实 HTTP 调用和编译器验证完整闭环，在工作台自有演示副本上注入变化并恢复，原始日志保存在 `build/workbench-validation/`。它会占用工作台任务执行通道，运行期间不要同时启动其他任务。
