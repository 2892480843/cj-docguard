# 参赛材料草稿与演示

本文是本地可审核素材，未替老陈报名、上传、发送邮件、签字或提交。最终规则及模板以主办方最新任务书为准。

## 项目摘要

CJ-DocGuard 是以仓颉原生实现的文档与示例验证工具。它从真实 AST 提取显式公共接口，将登记示例在实际 SDK 下独立编译运行，保存输出、退出码、断言和输入指纹。接口、示例、配置或工具链变化后，旧成功对当前项目失效；最新失败或未完成尝试不能被历史成功掩盖。静态报告和 AI 查询分别标明证据边界。

面向仓颉库维护者、使用陌生接口的开发者与 AI 编码助手，产物可以持续用于发布检查、内部开发、作品集及开源复用。没有宣称拿奖概率或首次发明文档生成/MCP。

## 已实现交付

- 仓颉原生 CLI、配置、语法提取、流式 SHA、输入/工具指纹、冻结快照、状态判定、严格门禁及报告。
- 离线搜索、源码入口、示例包装、逐项真实日志与断言、SDK 矩阵和链接诊断。
- 最新尝试优先、错误证据拒绝、显式归档及固定报告差异对比。
- C Unix 进程监督器；Python 标准库只读 MCP 适配、构建/测试/复现工具；语言构成透明。
- 47 公共符号、14 类健康样本，两个真实 SDK 共 28 格；错误注入测试与三项授权开源项目的固定版本报告。

实测数字与缺陷状态以 [验收记录](acceptance.md) 和实际 JSON/原始日志为准。第三方报告同时包含通过、未知和真实编译失败，不声称三个项目都采用了本工具。

## 三分钟演示脚本

1. **0:00–0:35** 展示健康报告：快照声明、接口、源码、SDK 及某个例子的精确输出断言。
2. **0:35–1:15** 在演示副本中把 `add` 的实现从加法改为减法，运行只读查询，旧记录为空；检查显示过期。
3. **1:15–1:50** 重新验证，展示真实断言失败；恢复加法，再验证，新的成功恢复准入。查看历史保留旧成功和失败。
4. **1:50–2:25** 展示同一输入的两 SDK 独立格，区分 26 个运行验证格和 2 个仅编译格。
5. **2:25–3:00** 展示 MCP 三只读工具及真实项目报告：为何实际运行过仍可能因未知输入而拒绝当前查询。

故障注入副本需明确标为演示构造，不混称真实上游缺陷。演示时可复制 `examples/healthy` 到临时目录，只修改副本；不要在最终报告生成后悄悄改源文件。现场时长以通知为准。

## 答辩可讲清的关键取舍

| 问题 | 回答依据 |
|---|---|
| 为什么原生 AST？ | 保留声明结构和位置，避免把正则匹配当成语法理解；不声称完整语义分析 |
| 为什么全项目失效？ | 首版减少漏依赖误放行，代价是查询时内容指纹和重验耗时 |
| 为什么成功后仍显示未知？ | 运行事实与当前输入充分性分开；外部输入未审核时不把一次运行当当前保证 |
| 为什么不能返回历史成功？ | 最新登记尝试优先，失败/取消/进行中都必须可见 |
| 为什么 C/Python？ | C 负责 Unix 进程组资源控制；Python 负责构建/协议；核心判断均为仓颉 |
| AI 改善效果证明了吗？ | 未做受控实验，只提供可复用证据接口，不宣称通过率提升 |

## 本地候选包

本次交付在 `build/release/` 保留源码 ZIP、冻结证据 ZIP 与 `manifest.json`（内容摘要与本地 Git 快照身份）。源码包不含 SDK、构建产物或私有历史；证据包含原始尝试、快照、日志及控制结果，未打包示例可执行程序。完整过去记录也保留于工作目录。

证据包属于冻结归档，不提供当前仓库证明；换环境后按 README 重新验证。原始日志/尝试保留实际本地路径，公开证据包前需由维护者审阅；源码包和证据包没有自动上传到远程。

可以从自己的本地 Git 快照重新导出源码：

```bash
mkdir -p build/release
git archive --format=zip --prefix=cj-docguard/ HEAD > build/release/cj-docguard-0.1.0-source.zip
```
